## Продуктовые границы первой версии

- Реализуй ровно три основные зоны: `Главная`, `Прогноз`, `Настройки`.
- Используй Open-Meteo Geocoding API для поиска и Open-Meteo Forecast API для погоды. API-ключи не нужны и не должны появляться в проекте.
- Интерфейс и пользовательские сообщения должны быть на русском языке; строки выноси в ресурсы.
- Не добавляй авторизацию, GPS/геолокацию, push-уведомления, виджеты, карты, аналитику, рекламу, backend, облачную синхронизацию, индивидуальное удаление или ручную сортировку городов без отдельного запроса.
- Вкладка `Месяц` показывает только реально доступный ответ API, максимум 16 дней. Всегда показывай подпись `Доступно до 16 дней` и предупреждение о снижении точности. Не генерируй прогноз до 30 дней.
- Дефолты первой версии: Celsius, светлая тема, не более 10 результатов поиска, debounce 400 мс, stale threshold 60 минут, фоновое обновление примерно раз в 3 часа. Режим `Как в системе` не добавляй.

## Технологический стек

- Kotlin для всего production-кода.
- Jetpack Compose и Material 3 для UI; XML layout-файлы экранов не добавляй.
- Navigation Compose для навигации.
- Koin для DI, включая ViewModel и Worker dependencies.
- Coroutines, Flow и StateFlow для асинхронности и реактивных данных.
- Room для избранных городов и последнего успешного погодного кэша.
- SharedPreferences только для небольших настроек, поскольку это требование PRD. Не мигрируй на DataStore в рамках первой версии без запроса.
- Retrofit для Open-Meteo: он уже выбран проектом. Не добавляй второй HTTP-клиент.
- WorkManager для уникального периодического обновления.
- Сохраняй заданные проектом `minSdk`, `targetSdk`, `compileSdk` и версии toolchain, если изменение не требуется самой задачей.
- Новую production-зависимость добавляй только при доказанной необходимости; сначала проверь, нельзя ли решить задачу текущим стеком или стандартной библиотекой.

## Архитектура и зависимости

- По подтверждённому пользователем заданию WF-023 постепенно выделяй физические Gradle-модули после проверки графа зависимостей. Не перемещай соседние слои одним массовым diff: каждый срез должен собираться и сохранять направленность зависимостей.
- Целевые области ответственности:
  - `core/model`: чистые Kotlin-модели, единицы, WMO mapping и время; без Android SDK, Retrofit, Room и Compose;
  - `core/network`: API, DTO и network data source;
  - `core/database`: Room entities, DAO, database и migrations;
  - `data`: repository implementations, координация remote/local источников и mapper'ы;
  - `domain`: repository contracts и use cases, когда они действительно переиспользуются или упрощают нетривиальную бизнес-логику;
  - `feature/<name>`: Compose UI, screen contracts и ViewModel конкретной функции;
  - `ui/theme` или будущий `core/ui`: тема и переиспользуемые UI-компоненты;
  - `di`: только сборка графа зависимостей;
  - `worker`: адаптер WorkManager, вызывающий внедрённую бизнес-операцию.
- Направление зависимостей: UI -> ViewModel -> domain contract/use case -> data implementation -> data sources. Чистые модели не зависят от внешних слоёв.
- Composable и ViewModel не обращаются напрямую к Retrofit, DAO, Room или SharedPreferences.
- Activity остаётся тонкой точкой входа: корневая тема, навигация и hosting UI; не размещай в ней данные или бизнес-логику.
- Не создавай формальные pass-through use cases без логики. Добавляй use case для переиспользуемой операции, координации нескольких repository или упрощения сложной ViewModel.
- Модульность выполняй только в WF-023; изменения публичных межмодульных API, Room schemas и test tasks проверяй на каждом срезе.

## Поток данных и UI state

- Следуй прагматичному MVVM + unidirectional data flow: state идёт вниз, UI events — вверх.
- ViewModel публикует immutable `StateFlow<UiState>` и не раскрывает `MutableStateFlow` наружу.
- Для сетевых экранов моделируй как минимум: initial loading, content, refresh поверх content, empty, error без cache, error с cache. Не заменяй сохранённый контент полноэкранным loader при refresh.
- Пользовательские действия передавай явными методами или типизированными actions. Одноразовые navigation/snackbar effects отделяй от долговечного state и не кодируй их флагом, который может повториться после recreation.
- Compose собирает Flow lifecycle-aware через `collectAsStateWithLifecycle`.
- Разделяй stateful Route и максимально stateless Screen: Screen получает state и callbacks, не создаёт зависимости и пригоден для preview/UI test.
- Не запускай сеть, SQL, тяжёлый parsing или запись настроек из Composable. Не выполняй тяжёлые преобразования на каждой recomposition.
- Сохраняй необходимое UI-состояние через ViewModel/SavedStateHandle или `rememberSaveable` в зависимости от владельца состояния.
- В маршрут прогноза передавай только стабильный идентификатор города; сам объект загружай из source of truth.

## Данные, сеть и offline-first поведение

- Room — single source of truth для избранных и последнего успешно сохранённого текущего/почасового/дневного прогноза.
- Типовой refresh: прочитать сохранённый город -> запросить API по координатам -> безопасно преобразовать DTO -> атомарно обновить Room -> позволить Flow обновить UI.
- При сетевой или parsing-ошибке не удаляй и не обнуляй последний успешный кэш. Покажи его с временем обновления и признаком устаревания.
- Храни температуру канонически в Celsius; Fahrenheit и единое округление применяй на presentation boundary без сетевого запроса.
- Сохраняй и используй timezone выбранного города. Не выдавай системное время устройства за локальное время города.
- DTO, entities, domain models и UI models не смешивай. Mapper'ы должны быть явными и тестируемыми.
- Поля внешнего API считай недоверенными: nullable поля и массивы разной длины не должны приводить к crash или неверному сдвигу данных. Объединяй массивы только по валидным индексам.
- Неизвестный WMO code преобразуй в нейтральное состояние `Неизвестно`, а не в исключение.
- Внутри data layer различай отсутствие сети, timeout, HTTP, parsing и отсутствие данных; пользователю показывай локализованные безопасные сообщения без HTTP-кодов и stack trace.
- Поиск не отправляет запросы короче двух символов, использует debounce 400 мс и отменяет/инвалидирует предыдущий запрос. Старый ответ не может заменить новый.
- Добавление города идемпотентно по стабильному идентификатору. Сначала сохраняй город; не удаляй его, если немедленный запрос погоды не удался.
- Не допускай параллельных одинаковых refresh одного города. Обновляй при возврате на главный экран только записи старше 60 минут.
- При изменении схемы Room добавляй migration и тест. Не используй destructive migration в release-коде без явного решения пользователя.

## Настройки и фоновые задачи

- Settings repository инкапсулирует SharedPreferences и публикует единый реактивный поток настроек.
- Запись настроек не инициируется напрямую из UI-компонента и не должна блокировать главный поток.
- Смена °C/°F и светлой/тёмной темы применяется ко всему видимому UI сразу и сохраняется после process restart.
- Очистка избранного и связанного кэша требует подтверждения и выполняется как одна согласованная операция.
- Регистрируй ровно одну unique periodic work request с `NetworkType.CONNECTED` и периодом около трёх часов.
- Worker получает зависимости через поддерживаемую Koin/WorkerFactory интеграцию или другой явно тестируемый constructor-based механизм. Не используй `GlobalContext` как service locator.
- Частичная ошибка одного города не отменяет успешные обновления остальных. Временная системная/сетевая ошибка даёт корректный retry/backoff; постоянная ошибка отдельного элемента диагностируется без бесконечного цикла.
- Worker никогда не стирает успешный кэш при ошибке и возвращает диагностируемый результат для тестов.

## Compose, UX и accessibility

- Используй Material 3 и одну корневую тему, управляемую реактивными настройками.
- Для смысловых иконок задавай локализованный `contentDescription`; декоративные иконки помечай как декоративные.
- Интерактивная область — не менее 48 dp. Не передавай смысл только цветом; поддерживай крупный системный шрифт и прокрутку в компактной/горизонтальной конфигурации.
- Для empty/loading/error/cache-stale состояний всегда показывай понятное объяснение и доступное следующее действие.
- Анимации должны быть короткими, ненавязчивыми, не блокировать ввод и не быть единственным носителем смысла.
- Не оставляй hardcoded demo data, шаблонный `Hello Android`, продуктовые строки в Kotlin, бессмысленные previews, TODO/FIXME или закомментированные альтернативные реализации в завершённой функции.

## Тестирование

- Добавляй тесты в том же изменении, что и production-логику. Сначала запускай самый узкий релевантный тест.
- Unit-тестами обязательно покрывай: Celsius/Fahrenheit и округление; WMO mapping; DTO/entity mapping; разные длины массивов; cache staleness; дедупликацию; отмену устаревшего поиска; ViewModel state transitions; error/cache/retry сценарии.
- Integration-тестами покрывай Room DAO и migrations, каскадную очистку кэша, настройки, JSON parsing и Worker с подменёнными зависимостями.
- Compose UI-тестами покрывай критические пользовательские пути и используй semantics, а не координаты/задержки: empty -> search -> add -> forecast, tabs, retry, settings и confirm/cancel clear.
- Тесты должны быть детерминированными: внедряй clock, dispatchers и fakes там, где код зависит от времени, конкурентности или сети. Не используй реальный Open-Meteo в unit/integration tests.
- Не ослабляй assertions, не отключай lint и не добавляй suppress вместо исправления причины без документированного обоснования.

## Безопасность изменений

- Не добавляй секреты, API keys и чувствительные значения в код, ресурсы, Gradle или логи.
- Release logging не должен содержать полные API responses, координаты пользователя как telemetry или внутренние исключения в UI.
- Не добавляй лишние Android permissions. Сеть работает только через HTTPS.
- Не выполняй destructive Git/filesystem операции, не стирай пользовательские изменения и не создавай Git-репозиторий без явного запроса.
- Не изменяй scope PRD молча. При настоящей продуктовой развилке представь рекомендацию, последствия и запроси решение; для обычной реализации используй дефолты PRD и продолжай автономно.
